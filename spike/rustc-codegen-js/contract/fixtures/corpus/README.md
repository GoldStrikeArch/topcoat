# corpus

One directory per construct family. Each pairs a Topcoat `view!` fixture with the
JSX that means the same thing, compiles the JSX with the pinned reference
compiler, and records what the compiled module does when it runs.

The corpus is the measuring stick for the Rust emitter. Nothing in it is
generated from the emitter, because the emitter does not compile most of it yet —
which is the point. The expected side exists first.

## Layout

```
<family>/
  view.rs                           hand-written  the Topcoat fixture (future input to OUR compiler)
  jsx.jsx                           hand-written  the equivalent JSX (input to the REFERENCE compiler)
  NOTES.md                          hand-written  why they are equivalent, and where they are not
  expected.reference.js             generated     compiled with PRESETS.dom
  expected.reference.hydratable.js  generated     compiled with PRESETS.domHydratable
  expected.reference.trace          generated     the dom output run against harness/trace.mjs
deltas.json                         hand-written  accepted divergences, per fixture
.prettierrc                         hand-written  upstream's own config, so corpus output formats identically
```

Regenerate the three generated files with:

```sh
node --import ./harness/register-loader.mjs harness/gen-corpus.mjs
```

It is wired into `run-all.mjs` ahead of `gen-tree-oracle.mjs`, which reads the
compiled output, so `run-all.mjs --check` covers the corpus like everything else.

`view.rs` is written in the shape of `view-dom-macro/tests/expand.rs` — a plain
`fn` per case returning `view_abi::Node` (or a tuple, for a multi-root body), and
one `#[test]` at the bottom that binds each without calling it. A family the
emitter supports can be dropped in as a test file unchanged.

Every column above is a fact about the REFERENCE side, regenerated by
`gen-corpus.mjs` from pinned upstream. What the Rust emitter does with each
family is a different question, it changes every wave, and this file used to
answer it in a `view-dom status` column that went two waves stale and ended up
contradicting the code. So it does not answer it any more. The answer lives in
one machine-readable place:

**`contract/fixtures/l2-status.json`** — one row per family: `MATCH`, `DIFFERS`
(with the count, the mechanically derived cause signature, and the named written
causes it is attributed to), `EXCLUDED` (with why), or `GAP` (with the blocker).
It is enforced, not merely recorded: `contract/harness/check-l2-status.mjs`
recomputes it and fails on any change in either direction, and it runs from both
`harness/run-all.mjs --check` and `parity/check.sh`.

```sh
cd contract/harness
node --import ./register-loader.mjs check-l2-status.mjs
```

Families 01–10 are derived from the upstream babel fixture families of the same
name, cut down so each exercises one thing. 11–17 are Topcoat-native: constructs
`view!` has that JSX does not, where the JSX side is the nearest Solid idiom
rather than a translation. 07b is a split of 07: same construct, but the thing it
measures is the hydration-key namespace a nested component opens rather than how
its props are passed.

## Equivalence levels

The corpus does not assert one kind of sameness. Three are useful, and they gate
in order — a family cannot be held to L2 before it passes L1.

**L0 — compiles.** The Rust emitter accepts `view.rs` without reporting an
unsupported construct. Which families reach it is live status, so it is not
listed here: a family that compiles has a fixture in `examples/dom-tests/`, and a
family with a fixture that also names a corpus family in its `NN.family` file has
a row in `contract/fixtures/l2-status.json` that is not `GAP`.

**L1 — template and walk parity.** Every `_$template` string the emitter produces
matches the reference byte for byte, and every hole's `firstChild`/`nextSibling`
path matches the one `fixtures/templates.jsonl` records for that template. This
is checkable without running anything, and it is where most emitter bugs will
show up: an off-by-one anchor changes a walk, and a changed walk is a wrong node.

**L2 — trace parity.** The emitter's module, run against `harness/trace.mjs`,
produces the same normalized call sequence as `expected.reference.trace` once
`deltas.json` is applied. Compared with `harness/compare-trace.mjs`, which erases
id numbering but preserves ordering, argument shapes, and aliasing.

Per family, the level each is *expected* to reach once its features land. This is
a statement of DESIGN INTENT, fixed when the corpus was written, and it is
deliberately not updated to track measurements — the whole point of keeping it is
that a family measured below its intent is a finding. Compare it against
`l2-status.json` rather than reading either as the other.

| level | families |
|---|---|
| L2 expected | 01, 02, 03, 04, 06, 07, 07b, 08, 10, 14, 15, 16, 17 |
| L1 expected, L2 open | 05, 09, 11, 12, 13 |

05 and 11–13 sit at L1 because the reference wraps conditionals and loops in
`memo`s and reconcilers whose Topcoat counterpart is a once-per-render server
loop — the first render agrees, later renders are a different design.
09 is L1 because the shared-`effect` / `_p$` record form for multiple dynamic
attributes is a code-shape decision not yet made.

Two of those intents have since been settled by measurement and are worth naming,
because both were written as open questions and are not open any more. 05's memo
gap CLOSED: `view_abi::cond` hands the test over as its own closure and the
backend emits `_$memo(() => test())`, recorded under `$measuredAndRetired` in
`examples/dom-tests/deltas.json` as `memo-hoisting-for-a-conditional`. 13's did
not, and cannot as written: the reference is a keyed reconciling `<For>` and
Topcoat's `for` is a Rust loop, which is the standing `keyed-list-vs-a-rust-loop`
cause.
07 and 07b were "equivalence undefined" until prop laziness was settled. It is
settled: a client component is a plain Rust fn with eager props, a reactive prop
is an explicit `Sig<T>` or closure, and child content is an eager `Node`. The
equivalence is stated in 07's NOTES.md as "a Topcoat component call is a Solid
`createComponent` call whose props object is destructured at the callee's
boundary", which is why every component in both JSX files destructures. 07 owns
the props story and 07b owns the hydration-key story, including the one permanent
divergence from Solid: eager child content is built before the component boundary,
so it takes slots in the caller's key context rather than the callee's.

## What `view-dom` refuses

Every construct the lowering rejects, read out of the `unsupported` and `error`
call sites in `view-dom/src/lower/` and `view-dom/src/dom_writer.rs`. Each entry
names the corpus families it blocks.

This section used to be a "NOT-YET-LOWERABLE ledger" listing `if`, `match`,
`for`, `let`, block, bind attribute and attribute spread as blocking errors, and
families 11–15 as not lowerable. **All of those now lower**, and families 11–15
all carry L2 verdicts. The list below is the one that matches the code; the
history is kept in this paragraph so the next reader can tell a refreshed
document from a stale one.

| construct | message | blocks |
|---|---|---|
| child nodes of a component | "child nodes of a component are not lowered yet" (`lower/component.rs:25`) | 07 (`with_children`), 07b (`children_component`) |
| `$(...)` as a component prop | "a runtime expression is not a component prop yet" (`lower/component.rs:49`) | 07, 07b (call sites avoid it) |
| `if` in an attribute list | `lower/attributes.rs:37` | 11 (the attribute-position form only) |
| `for` in an attribute list | `lower/attributes.rs:41` | 13 (the attribute-position form only) |
| `match` in an attribute list | `lower/attributes.rs:45` | 12 (the attribute-position form only) |
| `let` in an attribute list | `lower/attributes.rs:48` | 14 (the attribute-position form only) |
| block in an attribute list | `lower/attributes.rs:51` | — |
| `continue` in an attribute list | `lower/attributes.rs:54` | — |
| `break` in an attribute list | `lower/attributes.rs:59` | — |
| `continue` in a view body | `lower/node.rs:42` | — |

What lowers, in a view BODY, that this list once said did not: `if`/`else if`/
`else` with markup bodies, `match`, `for`, `let`, a block, a bind attribute, an
attribute spread, and a `signal` declaration (`lower/node.rs:21-32`,
`lower/local.rs:6`, `lower/bind_attribute.rs:9`, `lower/attributes.rs:23`).

Present but incomplete — measured gaps rather than refusals:

| construct | gap | affects |
|---|---|---|
| `setAttributeNS` | an `xlink:` or `xml:` attribute name is written with the plain `setAttribute`; no case in the corpus needs it | 09 |
| the shared `_p$` record | reactive attributes of one element are one `::view_abi::effect` each; the reference groups them into one effect carrying a previous-value record. The payload already carries the grouping in `Hole::effect_group` | 09, 15 |
| attribute versus property | every `name=(expr)` is `HoleKind::Attribute`; the reference decides from the name, and on a custom element writes a JS property. There is no Topcoat spelling for the override | 10 |
| `<"tag-name">` | the literal-string element name is accepted and lowered, and nothing tests what it lowers TO (`lower/element.rs:20`) | — |
| `delegateEvents` | emitted per instantiated template rather than unioned once at module scope; both register the same listeners | 04, 15 |

The last two are gate items rather than corpus facts, and the enumeration that
tracks them is `contract/G2-CHECKLIST.md` gate item 2, not this file.

## Accepted deltas

`deltas.json` declares differences that are understood and permanent, so they
stop failing a comparison without disappearing from view. Every rule needs a
`why` — `loadDeltas` refuses one without it — and a rule that matches nothing is
reported as STALE rather than passing quietly.

**The file loaded by the suites is `examples/dom-tests/deltas.json`, not this
one.** `scripts/dom-test.sh` points `--delta` there, and it took over in wave 4;
the copy here is a design record and says so in its own `$notLoaded` block. Add a
rule there, not here.

The five rules seeded here were predictions, and all five have since been
measured on first contact. `text-gt-escaping` did not occur — the reference
plugin constant-folds a string-literal child into the template and escapes it on
the way in, while view-dom treats `(expr)` as a dynamic hole whatever it holds,
so no escaping happens to differ over — and it was retired rather than left
standing. `component-props-object` and `component-fn-identity`, both
`ignore-field` on the `createComponent` record for families 07 and 07b, were
confirmed with their stated precondition checked: the emitter does wrap a
component call as `_$createComponent(thunk)`. Each outcome is written up in the
live file's `$measuredAndRetired`, and the resulting per-family verdict is
`contract/fixtures/l2-status.json`.

The live file also carries what the seeds could not: `$whatIsDeliberatelyNotHere`,
one written paragraph per divergence that is understood but is NOT a rule — a
difference in what is emitted is never a rule — naming the families it covers.
Those names are what `l2-status.json`'s `attribution` field cites, and citing one
that does not exist there is a check failure.

`$notExpressibleAsRules` is the companion list: divergences that are understood
but that no rule kind can state, with what it would take to state them. The one
entry is family 07's getter-children double `template.clone`, which is an artifact
of the trace harness rather than of either compiler.

Rules may equivalently live in a family's `NOTES.md` front matter — a `---`
delimited block whose body is JSON, not YAML, since this package has no
dependencies. `02-text-interpolation/NOTES.md` does that, so the justification
and the rule go stale together, visibly.

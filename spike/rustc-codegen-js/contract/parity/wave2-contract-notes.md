### Item 2 — what landed

NEW `parity/lib/keys.mjs`. The nested-key half of the comparison library, and the
runnable part of this item. It owns the letter encoding in BOTH directions:

- `hydrationKey(contextId, count)` -- moved here from `run.mjs`, which now imports
  and re-exports it, so one implementation serves the forward and inverse rules.
- `readSlot` / `keyChain(key, renderId)` -- THE CORE. A key is read left to right
  and the FIRST CHARACTER of the remainder fixes the next slot's width (a digit is
  a one-digit count; a letter promises `letter - 'a' + 2` digits). So a key parses
  into its chain of nested contexts deterministically, with no search and no
  ambiguity. This is what the letter is FOR, and it is what makes a nested key
  judgeable without running anything.
- `contextTree(keys, renderId)` -- reconstructs the context tree, since a
  component boundary writes no `data-hk` and the only evidence its context exists
  is that some deeper key nests through it. Reports duplicates, unparseable keys,
  per-context gaps, the derived boundaries, and the slot conflict below.
- `allocationOrder(keys, renderId)` -- the order the scheme spent the slots in,
  recovered from the strings by sorting on the count chain.
- `nestedKeyParity(root, {renderId, expected, components})` -- the entry point.
- `documentKeys`, `rootsByKey` -- the DOM-facing helpers a multi-template fixture
  needs to pair a template with the root it describes.

THE FINDING THAT SHAPED THE DESIGN, and the one wave 3 must not forget:
**document order is NOT allocation order.** Under eager child content a
component's child is built BEFORE the boundary is spent, so it carries a LOWER key
while sitting INSIDE the element with the higher one. `keys-nested.json`
`getterChildren` drives it: `<div data-hk="10"><span data-hk="0"></span></div>`.
A checker that walked the document and demanded a rising sequence would fail the
one layout Topcoat actually emits. So the sequence comparison is against a
declared ALLOCATION order recovered from the key strings, and document order is
reported alongside as information. Context nesting is not DOM nesting either, in
either direction.

HOW STRONG THE CHECK ACTUALLY IS -- measured, and written into the file, because
I first overstated it and the tests caught me. Parsing alone is weak: a key of
nothing but digits ALWAYS parses ("0123" reads as a key three boundaries deep), so
`keyChain` rejects only a broken letter promise, a leading zero after a letter, a
character that is neither, or a key outside the render id. The tightness comes
from two things layered on top, both in `nestedKeyParity`:
  1. `components`, the boundary count the fixture's SOURCE has. This is what turns
     "0123" from parseable into wrong.
  2. the slot conflict: a slot spent by an element that carries it cannot also be
     the context a deeper key nests under, because a slot is spent once.
Both are asserted, including the negative direction, so nobody reads more into a
green run than is there.

### A HARNESS HOLE I FOUND AND FIXED — worth reading, it cost me a false alarm

`capture-ssr.mjs --check` reported the counter's `ssr.html` as drifted, 2003 bytes
captured vs 2056 served. IT WAS NOT DRIFT. `withServer` spawned the demo-app
binary and then polled `fetch(ORIGIN + "/")` for a 200. A CONCURRENT AGENT was
running `topcoat dev` on port 3000, so my spawned binary died instantly with
`AddrInUse` (confirmed: `panicked ... Os { code: 48, kind: AddrInUse }`) while the
poll succeeded against the STRANGER, and the capture read its bytes. The one
difference was an injected `<script src="http://127.0.0.1:59039/dev.js">`, which
`crates/topcoat/src/dev.rs:58-67` renders whenever `TOPCOAT_DEV_URL` is set -- ON
A RANDOM PORT, so re-capturing would have committed a file that drifts on every
single run, and `--check` would have reported eternal drift against a capture that
was never wrong.

The `server.exitCode !== null` guard inside the poll loop cannot catch this: it
runs BEFORE the fetch, and on the first pass the child has not necessarily exited
yet. Fixed by refusing up front -- if anything answers `ORIGIN` before the spawn,
throw and say so, naming the dev-server case. With the port free, `--check` now
reports `ok counter /island 2003 bytes, unchanged`.

Consequence for the backend/framework agents: **do not re-capture parity SSR
bytes while a `topcoat dev` session is up**, and if a capture ever grows a
`dev.js` script tag, that is what happened.

#### CONTRACT-DOM.md section 14: "Async, and what an executor must respect"

11 new numbered points (14.1 to 14.11), every claim cited to the pin. Framed for the
BACKEND agent's async-vs-callback decision rather than as a survey. Still ASCII-only

The facts, in the order they matter:

- **14.1 The pinned runtime contains no async/await syntax at all.** Zero hits for
  `async function` / `async (` / `async x =>` / `await ` across every pinned solid and
  dom-expressions file. It is synchronous control flow plus explicit `.then()`. No
  `setTimeout`, no rAF, no rIC either; the one scheduler is `MessageChannel`-based
  (`solid.js:14-53`) and DORMANT unless `enableScheduling()` runs (`:528-530`, global
  `null` at `:171`). The only microtask in the DOM layer is `runHydrationEvents`
  (`client.js:310`). Two apparent hits are the STRING `"async"` in the
  boolean-attribute table (`constants.js:4`, `web.js:4`). So: an executor never has to
  interoperate with a runtime-internal await, because there is none.
- **14.2 An effect's return value is stored and replayed as its next argument.**
  `runComputation` (`solid.js:701-736`) does `nextValue = node.fn(value)` then stores
  it at `:733` (effects take the `node.value =` branch because `createComputation`
  omits `observers` while `createMemo` adds it at `:247`), and seeds the next run from
  it at `:689`. So an async effect body's PROMISE becomes the effect's value and
  arrives as `prev` next time. The runtime never inspects it; `isPromise` (`:256-258`)
  is `createResource`'s alone.
- **14.3 A tracking context does not survive a suspension point.** `Listener`/`Owner`
  are module globals (`:169`, `:173`) restored in a SYNCHRONOUS `finally`
  (`:705`, `:722-725`), which for an async fn fires at the first await. After the gap:
  reads do not subscribe (`:629`), `onCleanup` is a silent no-op (`:488-491`),
  `useContext` returns defaults (`:575-578`), created effects are unowned (`:755`),
  `getOwner()` is null (`:511-513`). `startTransition` (`:531-558`) is the one place
  upstream restores them across a microtask. => the executor must capture the owner
  BEFORE the first suspension and re-enter via `runWithOwner` (`:514-527`), because a
  Rust `async fn` gives the user nowhere to put that.
- **14.4 A rejected Promise is invisible to the runtime's error handling.** The only
  path is the synchronous catch at `:708-721`; `catchError` (`:492-507`) and
  `ErrorBoundary` (`:1543`) are synchronous too. A rejection is a host-level unhandled
  rejection. => no upstream safety net for a Rust `Err` delivered via rejection.
- **14.5 A batch closes at the first suspension point.** `batch` is
  `runUpdates(fn, false)` (`:452-454`); `runUpdates` (`:816-831`) calls
  `completeUpdates` synchronously on the next line and `Effects` is nulled at
  `:872-875`. A `createEffect` from a continuation finds the queue null and runs
  immediately and unbatched (`:228`). => microtask-resumed futures get no batching.
- **14.6 THE BIG ONE. Hydration's window is exactly one synchronous call stack.**
  `hydrate` clears `sharedConfig.context` in a synchronous `finally`
  (`client.js:256-261`, prod `web.js:357-366`), so after a suspension `isHydrating()`
  is false (`client.js:330-332`) and `getNextElement` takes `return template()`
  (`client.js:275`) -- it BUILDS FRESH DOM instead of adopting the server's, and the
  mismatch throw is DEV-ONLY (`client.js:269-274`, absent from `web.js:368-378`), so
  in production it is entirely silent. Five further breakages cited (key desync,
  consumed registry, nodes never added to `completed`, `count` cannot hold the window,
  leaked `onCleanup`). => **an island's setup must be synchronous.**
- **14.7 The only sanctioned way to hold the window open is open-coded twice**, in
  `lazy` (`:1433-1467`) and `Suspense` (`:1636-1726`): capture the context, maintain
  `sharedConfig.count`, re-install with `setHydrateContext(ctx)` inside `.then` while
  checking `done`. `count` is written ONLY by `lazy` (`:1440-1441`), so nothing else
  can register outstanding async work; `runUserEffects` consults it (`:904-916`).
  Instructive by omission: `startTransition` restores the reactive globals and NOT
  `sharedConfig`, so the two are separate obligations.
- **14.8 A delegated event during an async gap ends hydration permanently.**
  `client.js:436` with the source's own comment `// cancel hydration`. `_$HY.done`
  starts falsy (`server.js:538-544` sets no `done`); once true, `hydrate` degrades to
  a plain client render on entry (`client.js:245`). `runHydrationEvents` also BAILS on
  the first target not yet in `completed` (`:316`), stalling the whole replay queue.
  => the strongest single argument for 14.6.
- **14.9 Promise detection upstream is a PROPERTY test, not a callable test:**
  `v && typeof v === "object" && "then" in v` (`:256-258`). Not typeof-function, not
  instanceof. `createResource` accepts three fetcher shapes (`:353-381`), including a
  settled `v`/`s` marker checked BEFORE `.then` (`:371-374`); rejections surface only
  on read and only when nothing is in flight (`:328`); a superseded request is dropped
  by `if (pr === p)` (`:297`); reading a pending resource outside Suspense neither
  throws nor suspends, it returns the initial value (`:324-341`). => a Rust-future
  surrogate must not carry a `then` property unless it is genuinely thenable.
  **Topcoat's existing browser runtime already gets the shape right and it is worth
  keeping**: `crates/topcoat-runtime/browser/src/surrogate/future.ts:1-23` is a LAZY

- **14.10 A Promise inserted into the DOM is silently dropped.** `insertExpression`
  (`client.js:461-546`) falls off the end at `:543` into a dev-only warn; prod

  and reports nothing.
- **14.11 There is no cancellation anywhere in the pin.** Zero hits for
  `AbortController`/`AbortSignal`/`abort`. `createResource` passes only
  `{ value, refetching }` (`:355-358`), and its `onCleanup` (`:286-291`) nulls the

  Guarded by `if (Owner)`, so a resource outside an owner has no cleanup at all.
  => dropping a Rust future is expected to cancel; nothing upstream does.

#### PROCEDURES.md + fixtures/procedure-wire.json + the gate

`contract/PROCEDURES.md` is the prose page; `fixtures/procedure-wire.json` is the
machine-readable half, 19 vectors; `harness/check-procedure-wire.mjs` is a new

THE WIRE, as specified:
- `POST /_topcoat/procedures/{id}`, POST only (`Methods::Only(&[Method::POST])`,
  `src/procedure.rs:184-187`); other methods 405, unknown id 404.
- The id is a **v4 UUID minted at MACRO-EXPANSION time**
  (`grammar/src/procedure.rs:123`), so it is stable for a binary and NOT across
  rebuilds. A client and server from different builds do not share ids. Flagged as the
  most important operational fact on the page.
- TWO WIRES, told apart by request media type:
  * surrogate (`#[procedure]`, today's only wire): `application/json`, args = array of
    `dehydrate()` forms, **zero args = `null`**, response `application/json`.
  * serde (`#[procedure(serde)]`, specified not landed): `application/topcoat+json`,
    args = array by `Serialize`, **zero args = `[]`**, response `application/json`.
- Each wire REJECTS the other's zero-arg spelling, which is what makes the asymmetry
  safe rather than a trap. Both directions pinned (`src/procedure.rs:302-323`).
- One argument is still an ARRAY (`[value]`), because the tuple is `(T,)`.
- Media type matching: split on `;`, trim, case-insensitive (`:56-66`).
- Exclusive wires, with the bounds argument for WHY: both branches in one handler
  would put `A: Surrogated + R: Surrogated` on every serde procedure, which is exactly
  what the feature exists to escape.
- ERRORS are `text/plain`, no JSON envelope: 400 `bad request: {description}` or
  `bad request: {description} (at `{path}`)`, where the path is the argument's
  zero-based index, so `` (at `1`) `` means the second argument. 400 not 415 (D2).
  Handler errors go through the router's ordinary `error_into_response`
  (`error.rs:34-53`); anything unmapped is a 500 whose body is the literal
  `internal server error` with nothing about the cause.
